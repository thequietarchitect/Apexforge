## Reference and correlation model

`SourceReference` retains the existing document identity and exact end-exclusive source span, plus the producer's `(air_id, kind, reference)` construct identity. Source positions preserve line, column, and character offset; the document fingerprint preserves exact UTF-8 content. No host path or source text is retained in the projected reference.

`AIRReference` wraps the existing structural `OperationReference`. Its operation ID, AIR fingerprint, ordinal, and typed occurrence locator remain canonical metadata evidence. Assignment locators supply directive association; state initialization has no invented directive association.

`NativeRegionReference` identifies the existing generated `program.c` document/span, operation ID, native mapping fingerprint, and metadata association fingerprint. Optional retained artifact references carry image, receipt, result, and scope fingerprints only after the supplied `NativeResultAssociation` matches an externally captured association fingerprint and the execution's linked `ProvenanceScope`. The scope must agree on AIR, routing, sidecar, source mapping, native mapping, profile, generated bytes, and metadata association.

Machine-address availability is explicitly `unsupported`. There is no machine address, instruction pointer, CPU range, PDB symbol, OS handle, or artifact path in this model. Missing artifact references mean no artifact association was supplied; region evidence alone does not prove a native executable ran.

`CorrelationChain` combines one execution reference, one AIR reference, and source/native candidate sets. `CorrelationIndex` binds the ordered chains and mapping identities to one session and execution. Supported partial chains include:

| Supplied evidence | Source | AIR | Generated native region |
| --- | --- | --- | --- |
| Real compiler output on a non-native path | available | available | not_applicable |
| Admitted hand-built AIR with native mapping | unavailable | available | available |
| Source evidence with no supplied backend mapping | available | available | unavailable |
| Operation without source evidence | unavailable | available | available or unavailable according to supplied native evidence |

The record shape also supports all three layers when a legitimate producer supplies an identity-consistent complete chain. No ordinary compiler-produced complete native chain is claimed or fabricated in this stage.

## Availability, synthetic origin, and ambiguity

The correlation availability enum follows P13.3's available/unavailable/unsupported/not_applicable terminology and adds `ambiguous` locally without changing the frozen incoming inspection module. Correlation references contain no semantic value payload requiring `redacted`; P13.3's sensitive-value boundary is preserved.

Candidate records enforce explicit status and payload agreement. Missing evidence has no fabricated empty span or zero address. More than one distinct producer-supported source candidate yields `ambiguous`, retains every candidate, and sorts their canonical forms deterministically. No first-candidate preference is applied.

The ordinary P12 source-mapping producer rejects ambiguous primary correspondence. The focused ambiguity test uses a controlled producer-side sidecar containing multiple explicit valid `EvidenceReference` links to existing compiler map entries. It tests preservation in the debugger projection, not a claim that the ordinary compiler now produces ambiguous primary mappings.

`inspect_lineage` projects existing structural lineage separately. Synthetic principal/authority objects have `owned_source=unavailable`; a recorded originating directive remains a separate origin link. Generated containers and metadata-only records likewise acquire no owned physical syntax. These origin links never become source-step targets. Only the frozen state/assignment operation locator surfaces are represented; no new locator is invented for unsupported nested/synthetic operations.

## Ordering and supplied current position

Metadata operation ordinals are preserved exactly: state initialization followed by the recorded structural directive/decision/path assignment occurrences. This is canonical metadata enumeration, not a universally executable semantic schedule. It includes structural alternatives and does not cover every compiler action or nested operation. Generated-C line order, source order, event order, and causal order are not substituted for this enumeration.

`ObservedPosition` is supplied by the execution/observation owner. It names session, execution, correlation-index fingerprint, operation ID, observation occurrence, and supporting observation reference. It is not a live program counter and cannot discover a current instruction.

`KnownObservationOrder` is a separately supplied resolved observation window starting at that position. It names each operation in owner-established order, a supporting evidence reference, optional confirmed directive boundaries, and whether that window is complete. Repeated operation IDs are permitted for separately observed occurrences. Completion describes the evidence window, not completion of execution.

The layer checks all IDs against the bound index; it does not verify a trace payload or choose a causal path. The embedding owner must establish the resolved order from legitimate canonical evidence. Metadata adjacency alone never authorizes planning the next runtime operation.

## Step targets and pure planning

`StepTarget` is an immutable observation destination: mode, bound session/execution/index, correlation chain, `(observation occurrence, metadata ordinal)` ordering key, and evidence reference. It has no callback, control request, runtime handle, or mutation method. A target validates against the exact bound chain and current active session.

`StepPlan` records the supplied position, mode, availability, target tuple, and explanatory reason. It is a deterministic observational value. Constructing or accepting it advances nothing and grants no execution-control rights.

| Mode | Implemented planning behavior |
| --- | --- |
| `SEMANTIC_STEP` | Returns the next operation in the supplied resolved window. Without it, returns `unavailable: needs_runtime_observation`, even if a metadata-adjacent operation exists. |
| `SOURCE_STEP` | Requires one reliable current source location. In the resolved window, collapses operations with the same document/span, skips explicitly unmapped operations, and returns the next different mapped span. Semantic mode can still represent the skipped operations. |
| `DIRECTIVE_STEP` | Returns a supplied confirmed boundary whose directive identity agrees with that operation's assignment locator. Declaration order never establishes directive activation. Missing boundary evidence remains unavailable. |
| `NATIVE_CORRELATION_STEP` | Returns the generated region for the currently supplied semantic operation. It does not advance to another C line or execute anything. Missing mapping retains its availability status. |
| `WORKFLOW_STEP` | Explicitly unsupported: there is no consumed evidence-backed workflow ordering contract in this foundation. |

An ambiguous prospective source operation returns an ambiguous plan with all source candidates retained in its target chain. An unmapped or ambiguous current source position cannot establish the baseline for a distinct-span step; it returns unavailable and directs the caller to semantic mode. No nearest-source convenience mapping is attached.

A complete evidence window with no further qualifying target returns `not_applicable: no_more_targets_in_supplied_window`. An incomplete window returns `unavailable: needs_runtime_observation`. Neither result predicts a branch or asserts runtime completion.

Preserved distinctions:

```text
CORRELATION != EXECUTION
STEP_PLAN != STEP_EXECUTION
SOURCE_STEP_TARGET != SOURCE_EXECUTION
SEMANTIC_STEP_TARGET != AIR_EVALUATION
NATIVE_CORRELATION_STEP != MACHINE_INSTRUCTION_STEP
OBSERVED_POSITION != LIVE_PROGRAM_COUNTER
```

## Session binding and inspection integration

Building an index, planning, and validating targets require the P13.2 session to be active, grant observe, and retain the exact execution target. Cross-session references, different execution-local IDs, stale index fingerprints, wrong AIR programs, wrong routing, and closed sessions are rejected. The observe capability does not imply control authority; an observer-only session can plan without dispatching control.

`correlate_inspection` accepts a P13.3 `SessionInspection` and an explicitly supplied operation ID, checks the same session/execution binding, and returns the matching immutable chain. It does not infer current position from state values, modify the inspection, or wrap execution. Historical reference values may be retained, but using them to plan requires a current valid active session.

## Determinism and security/integrity

Canonical forms are schema-versioned in-memory fingerprint preimages, not a new public transport or persistence parser. Equivalent records produce equal forms/fingerprints. Source candidates are canonically ordered; AIR chains preserve metadata ordinals; observation order remains explicitly supplied.

Position timestamps are optional observational metadata excluded from equality and canonical fingerprints, including target/plan fingerprints derived from that position. Session/execution-local references are deliberately binding identities, not stable semantic identities. Temporary build roots, PID, address, timings, UI state, and network connection identity have no fields in the stable forms.

There is no client-supplied path reading, compilation, native launch, artifact writing, provenance mutation, runtime state access, or execution dispatch in `debug_correlation.py`. Immutable mapping types are imported; their execution-producing helpers are not called. Static AST checks and runtime traps cover AIR runner, RuntimeEngine execution, native dispatch/emission/admission, plan binding, compiler invocation, process launch, and file reads/writes. Existing metadata validation uses deterministic AIR serialization and typed occurrence validation only.

Retained artifact fingerprints are checked against owner-supplied association anchors. The focused real native fixture executes through the existing owner before correlation traps are installed, then verifies unchanged retained evidence and rejects a substituted image association. The correlation layer never reads the deleted executable or consumes its dispatch ticket.

## Resource custody

No new mutable manager or live resource is introduced. Session-bound correlation indexes and observation windows are operational retained values under the P13.2 session owner's existing DHF custody. Transient plans are IRR-style observations; canonical/source/native/provenance fingerprints reference existing evidence whose retention remains with its original owner. Closing a session invalidates planning without deleting canonical evidence.

Known owner: the authorized session/observation owner. Known purpose: correlation and observation-target navigation. Known lifetime: session-local planning, or deliberate retained evidence references. Valid binding: exact session/execution/index plus existing AIR/mapping/provenance associations. MSC remains an analytical resource-continuity lens, with no semantic or execution dependency.
