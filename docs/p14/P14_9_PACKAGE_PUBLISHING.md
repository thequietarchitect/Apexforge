## Contract census and scope

P14.1 immutable manifests/content identities and P14.6 ContentMember/verify_integrity are REUSE. P14.8 RegistryCatalog, RegistryRecord and RegistryBlob are REUSE; its protocol remains read-only. P14.3 lock identities and P14.5 compatibility are REFERENCE_ONLY: publication neither changes locks nor computes compatibility. Existing AuthorityEngine principals, roles and grants are FROZEN_AUTHORITY_CONTRACT, not publication credentials. PublisherPrincipal, PublicationGrant and PublicationPolicy are REGISTRY_LOCAL_POLICY.

P14.6 retains CRYPTO_PROVIDER_UNAVAILABLE. Passive signature envelopes remain structural evidence; actual asymmetric signature verification and cryptographic publisher authentication remain unavailable. No provider was installed and no dependency metadata changed.

## Principal and exact namespace policy

PublisherPrincipal is an opaque registry-local identifier with bounded ASCII grammar `[a-z][a-z0-9_-]{0,63}`. This syntax conveys no human, organization, email, machine-user, package-author or namespace identity. It is a distinct typed domain from runtime authority principals.

Publisher authentication is an EXTERNAL_PRECONDITION. The engine accepts a caller-supplied principal and checks registry-local permission; it does not authenticate that caller. There is no authenticated Boolean or cryptographic authentication claim.

PublicationPolicy is frozen, sorted by principal identifier then exact namespace, and deduplicates identical grants. Every grant is principal -> exact validated package namespace. Parent/child scopes do not inherit permission. No delegation, transfer, prefix grants or ownership inference exists. Package namespace != organization; publication grant != namespace ownership proof. Policy fingerprints use SHA-256 over canonical JSON with the domain `apexforge.registry-publication-policy/v1` plus NUL.

## Request, validation and integrity

PublicationRequest schema is `apexforge.registry-publication/v1`, distinct from the P14.8 read protocol. It carries a validated manifest, principal, exact expected PackageContentIdentity, supplied in-memory member bytes and optional passive SignatureEnvelope. Frozen inputs and deterministically sorted logical member paths produce canonical JSON with sorted keys, stable compact separators, ASCII escaping and no volatile host data.

Construction checks schema, principal, validated manifest/content/member types and optional envelope type. Envelope structural validation belongs to the existing P14.6 constructor; no signature verification is performed. Publication then checks catalog/request types, P14.6 actual-byte integrity, expected content identity, policy type, exact namespace grant, existing coordinate state, and supplied-member/blob consistency. Only after all gates does it construct a resulting catalog and receipt.

Integrity checks the exact member set and raw SHA-256 digests. Missing, unexpected, modified and duplicate members fail publication. Content identity must exactly match the manifest's P14.1 canonical identity. Non-identity presentation metadata remains excluded and cannot authenticate an author or publisher.

## Immutable coordinate and state transition

An empty coordinate admits exact canonical content as PUBLISHED_NEW in a new immutable RegistryCatalog. Existing coordinate plus different content fails PUBLICATION_COORDINATE_CONTENT_CONFLICT. Externally divergent P14.8 catalogs also fail publication at that coordinate, independent of record order. P14.8 remains able to represent such external divergence.

An authorized identical retry returns ALREADY_PRESENT and the original catalog object, without adding records or blobs. Integrity and namespace permission are still checked. Retry preserves the existing passive signature envelope rather than editing evidence. A retry cannot repair an existing record with missing required blobs. Changed canonical content requires a new coordinate under this publication policy; publishing an explicitly supplied new version is supported without selecting versions.

Blob bytes are validated before creating RegistryBlob. Identical digest/bytes reuse existing blobs, including across distinct packages. Existing digest/different bytes fails PUBLICATION_BLOB_CONFLICT without overwrite. Temporary local dictionaries are not observable registry state; no partial package or success receipt is returned on failure. The input catalog is never mutated.

## Receipts, provenance and determinism

PublicationReceipt is generated internally by publish as immutable canonical JSON. It binds principal, exact coordinate/content, status, policy fingerprint, before/after state fingerprints, package provenance references, external-authentication status and UNSIGNED/NOT_VERIFIED signature status. record() returns a detached parsed copy. It is not a raw receipt parser or an independent authentication proof.

Receipt fingerprint domain: `apexforge.registry-publication-receipt/v1`.
Full registry transition fingerprint domain: `apexforge.registry-publication-state/v1`.
Both use SHA-256(domain + NUL + canonical JSON UTF-8). Full state includes canonical records and ordered blob digest/hex-byte records. This deliberately differs from P14.8's record-only discovery snapshot fingerprint. Neither becomes package identity, trust or authority.

No timestamps, random UUIDs, host paths or local handles enter receipts. Equivalent policy/catalog order permutations yield equivalent transitions and receipts. Provenance references are preserved, not rewritten into registry-origin claims. Publication receipt != authorship proof; publication event != package origin; publisher principal != package author. EVIDENCE_BEFORE_ATTRIBUTION=True.

## Interoperability and separation

The resulting catalog supports unchanged P14.8 coordinate/content queries, exact-version listing, blob retrieval and candidate snapshots. P14.8 has no publish/delete/yank request operation. P14.9 does not invoke the dependency solver, update lockfiles, insert into cache, evaluate capability compatibility, grant package trust or invoke AuthorityEngine. Published capabilities remain declarations; publishing does not establish compatibility for consumers.

Passive signatures stay NOT_VERIFIED; registry presence is neither a trust anchor nor a signature verdict. Publication policy is independent of P14.6 trust policy and runtime authority. No package install/execution, filesystem discovery, network publication transport, private-key persistence or fake authentication exists. Delete/yank/unpublish, namespace transfer/delegation/inheritance, migration, packaging, supply-chain certification and closure/freeze remain deferred.
