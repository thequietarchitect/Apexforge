## Input and explicit profiles

SupplyChainEvidence is a frozen input wrapper over caller-supplied validated package contracts and optional evidence. It accepts a manifest, exact member bytes, optional expected identity, resolved graph, lock, registry record/catalog, publication receipt/before/after/policy, artifact bundle, supplied build bytes/fingerprints, canonical AIR references, passive signature/key/policy, in-memory cache entry, contextual compatibility report and logical source bytes.

SuppliedBuild binds a descriptor logical PackagePath to supplied build bytes and producer fingerprint, with optional generated-source bytes. There is no filesystem path read, artifact discovery, registry query or evidence acquisition. This wrapper does not authenticate producer claims or manufacture absent evidence.

ValidationProfile is frozen. Its supported requirement table is immutable and caller-selected:

| Profile | Required evidence |
|---|---|
| PACKAGE_INTEGRITY | Manifest and supplied package members |
| LOCK_RESTORE_CHAIN | Members and lock |
| REGISTRY_PUBLICATION_CHAIN | Members, exact record/catalog, receipt, before/after state and publication policy |
| PACKAGE_ARTIFACT_CHAIN | Members, bundle, supplied build evidence and canonical AIR references |
| FULL_STRUCTURAL_SUPPLY_CHAIN | Members, lock, registry/publication transition and artifact/build/AIR evidence |

Optional require_authentication is explicit; it does not change package identity or silently alter requirements. A signature is required when that flag is true. No profile discovers evidence or automatically escalates because extra objects happen to be present. Supplied associations are checked even under a smaller structural profile; contradictions cannot be ignored merely because their evidence was optional.

This is bounded structural composition, not a claim that every optional provenance/semantic-history link exists. Original source-to-AIR compilation correctness, native backend issuance, signed historical provenance, package execution and authenticated publisher identity remain outside the available evidence.

## Result semantics and authentication honesty

The report has overall status, structural_status and a separate authentication record:

- VALID: the selected structural profile's required evidence is present and consistent.
- INVALID: contradictory or malformed supplied evidence fails a checked association.
- INCOMPLETE: required evidence is absent, with no stronger invalid finding.
- UNVERIFIED: structural_status is VALID but caller-required authentication cannot be established.

Invalid takes precedence over incomplete; missing optional evidence is NOT_APPLICABLE with MISSING_OPTIONAL_EVIDENCE. Missing required evidence has SUPPLY_CHAIN_REQUIRED_EVIDENCE_MISSING and INCOMPLETE. Structurally valid signatures remain UNVERIFIED in the authentication dimension even when a structural-only profile has overall VALID. That VALID means structural validation only; it is never cryptographic trust PASS.

Authentication always records CRYPTO_PROVIDER_UNAVAILABLE, cryptographic provenance UNAVAILABLE, publisher EXTERNAL_PRECONDITION and final_trust NOT_ESTABLISHED. No SIGNATURE_VERIFIED=True, package trust grant or real-world attribution is produced. Unsupplied authentication is NOT_SUPPLIED; required absent signature produces INCOMPLETE, distinct from a malformed signature.

## Package integrity and exact lock/dependency binding

Manifest admission reuses P14.1 construction validation and canonical content_identity(). Optional expected content must match exactly. Package member validation delegates to P14.6 verify_integrity: exact member set, logical paths, actual raw digests, missing/extra/modified/duplicate members. No second content hash algorithm or directory scan exists.

Graph/lock evidence must contain the exact package coordinate and content identity. A supplied graph and lock must describe the same resolution. Substitution fails SUPPLY_CHAIN_LOCK_MISMATCH. Report nodes retain resolved exact references and existing directed dependencies. The validator does not solve, select candidates, produce a restore plan or modify lock data.

## Registry and publication binding

RegistryRecord is structurally re-admitted using existing P14.8 parsing/association checks. Its exact coordinate/content must match the package. Registry catalogs must have one unambiguous matching coordinate record and valid referenced member blobs; a supplied standalone record must agree with the catalog. Required member digests are rechecked against supplied catalog bytes. Presence never grants trust.

Publication receipt JSON uses P14.11's bounded duplicate-key-safe parser and an exact current P14.9 receipt field set. The validator checks schema, principal grammar, package coordinate/content, status, canonical provenance references, signature-status honesty, external-authentication boundary, false authority/trust-grant flags and fingerprint syntax.

When before/after/policy are supplied, the receipt must bind their exact full registry-state and policy fingerprints. Its principal must have the exact namespace grant. PUBLISHED_NEW requires no existing coordinate in the prior state, exact added record and exact prior/member blob union without conflicting overwrite. ALREADY_PRESENT requires unchanged state. The resulting record and blobs must match package content; supplied registry state must equal the after state. Missing transition evidence is incomplete under a profile requiring publication, otherwise an explicitly missing optional association.

The engine is not called to reproduce the publication. Comparing supplied state/receipt claims does not execute publication or authenticate a publisher. Receipt != authorship proof; publication event != package origin. Namespace grants are registry-local policy, not ownership.

Passive envelopes transported by a registry catalog or after-state record are independently structurally admitted and checked against the current package signing payload. Contradictory standalone/carried envelopes fail; transported evidence cannot silently become verified.

## Artifact, build, AIR and native/hybrid continuity

P14.11 descriptors/payloads/bundle are re-admitted. Package identity, exact byte-digest sets, immutable variant/path rules and supported target/profile checks remain unchanged. Any corrupt included variant fails the claimed bundle: a valid managed descriptor cannot validate or conceal a corrupt native descriptor. No invalid variant is discarded to obtain success.

Build evidence is keyed by exact descriptor logical path, with duplicate/unassociated build-path conflicts rejected during artifact-chain validation. Managed data must verify under the existing P11 envelope fingerprint convention and match descriptor raw bytes/build reference. Native image/receipt must pass existing P14.11 receipt/fingerprint/image checks. Entry references retain existing exact-build-entry rules.

Build AIR references and separately supplied canonical AIR references are compared by exact schema/kind/fingerprint. Missing per-artifact build or AIR evidence is incomplete under artifact-required profiles. Human display names are not identity. Artifact source/provenance references must agree with the re-admitted build/package evidence.

Native target/profile remains exactly win-x64 / apexforge.native.win-x64.i64-literal-state-set/v1. Widening fails SUPPLY_CHAIN_NATIVE_PROFILE_MISMATCH. Managed means the current AIR-oriented build representation, not a standalone .NET backend. Native transport fixtures prove association/integrity only, not PE validity, backend ticket issuance, compiler success or behavior.

## Source and provenance continuity

Managed build project sources are validated as logical relative paths plus raw SHA-256 claims; source_count and source list must agree and paths cannot duplicate. Supplied source bytes must match exact declared hashes. Missing bytes for a declared source are incomplete under an artifact/build-required profile. No source is fetched or inferred from similar names.

Native receipt-generated-source reference is a generated-C digest, not an authored source identity. If generated-source bytes are supplied with SuppliedBuild, they must match that reference. Their absence remains MISSING_OPTIONAL_EVIDENCE because existing retained native receipts need not retain generated source bytes.

The report records BUILD_DECLARES_SOURCE, SOURCE_BYTES_MATCH_BUILD_REFERENCE and BUILD_REFERENCES_GENERATED_SOURCE claims only when supported. It does not assert that matching source bytes prove compiler history or semantic correctness. A source hash/reference does not alone establish SOURCE_PRODUCES_AIR.

Package provenance syntax is already P14.1-owned; continuity is checked across registry records, publication receipt and artifact descriptors. Mutated references fail association or provenance diagnostics. Referenced historical statements and debug mapping semantics are not authenticated or independently replayed.

## Signature, trust policy, cache and compatibility

SignatureEnvelope is structurally reconstructed under P14.6 schema/algorithm/length/digest rules. Its payload fingerprint must commit to the current package identity. Malformed envelope and package-payload contradictions are invalid; correct structure remains unverified.

Existing verify_package is used only for supplied key/policy observations: signer-key mismatch is invalid; policy scope eligibility is labeled an observation and final cryptographic trust remains NOT_ESTABLISHED. Policy approval never substitutes for signature verification. No crypto dependency, fake primitive, private-key storage or network trust discovery was added.

CacheEntry inputs are in-memory evidence, not cache roots or handles. Existing entry construction rechecks member integrity and exact package content. No cache get/put/filesystem access occurs, and presence is not trust.

P14.10 compatibility reports are contextual NON_SUPPLY_CHAIN_METADATA. Their structural classifications do not prove integrity/authenticity, select an upgrade or grant runtime authority.

## Deterministic graph, diagnostics and report identity

Evidence nodes include exact package identity/manifest, member integrity, resolved nodes, lock/graph fingerprints, registry record/state, publication receipt/policy, independent artifact descriptors/payload/build references, source/AIR references, provenance, passive signatures and policy/context observations where supplied and associated.

Nodes use SHA-256(`apexforge.supply-chain-evidence-node/v1` + NUL + canonical kind/record JSON UTF-8). Their category remains separate from identity. Exact duplicate nodes are deduplicated. Edges record claim/source/target/status; checks and diagnostics preserve stable codes. Invalid and incomplete associations never create a VALID claim to conceal the break.

Canonical node ordering is fingerprint order; edges/checks/diagnostics use lexicographic tuple order. JSON has sorted keys, compact separators, ASCII escaping, UTF-8, no timestamps, random IDs, host paths or usernames. Records are detached copies; reports are frozen canonical JSON.

Report fingerprint uses `apexforge.package-supply-chain-validation/v1` + NUL + canonical report JSON UTF-8. It commits to selected profile, exact package, admitted evidence graph, statuses and diagnostics. It is neither package identity nor trust/authorization identity.

Representative codes distinguish package/content, lock, registry, publication, artifact package/digest, build/AIR, native profile, provenance, signature, cache and missing-evidence failures. Exception text is never the canonical identity of a failure.

## Security and non-acquisition boundary

The production module has no direct filesystem, process, network, compiler, RuntimeEngine, native dispatch or AuthorityEngine access. It invokes in-memory integrity/association helpers only. It does not publish, solve, alter locks/manifests/cache, install or execute artifacts, or persist keys.

Focused mocks prohibit solve, publish, RegistryCatalog.query, PackageCache.put, RuntimeEngine.execute, AuthorityEngine.check and native build/dispatch. AST assertions inspect prohibited imports/calls. All traps remain unused.

EVIDENCE_BEFORE_ATTRIBUTION=True. A report can state that supplied artifact/build/package/receipt identities match; it cannot assert a human/company authored or authenticated them.
