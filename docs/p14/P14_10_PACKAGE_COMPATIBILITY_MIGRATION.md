## Comparison scope and model

`compare_packages(old, new, old_exports=None, new_exports=None)` consumes validated PackageManifest values. Namespace/name define the package identity family. Different families produce PACKAGE_IDENTITY_FAMILY_CHANGED; no rename is inferred. Exact version is recorded as context through old/new coordinates, but never used to decide compatibility. Upgrades and downgrades use the same structural rules.

CompatibilityReport retains old/new exact identities, frozen PackageChange records, dimensional observations, overall classification, explicit structural-compatibility status, provenance and NOT_ESTABLISHED behavioral equivalence. Change records carry dimension, deterministic reason, classification and canonical old/new JSON values. Human prose is not a reason identity.

Overall precedence is family change, incompatible schema, breaking structural change, unknown, additive, identical. Breaking findings are retained even if other evidence is unknown. A breaking overall report does not erase unknown dimensions. Unknown is never structurally compatible.

| Status | Meaning |
|---|---|
| IDENTICAL_CONTRACT | No changed measured public structure; not identical contents or behavioral equivalence |
| COMPATIBLE_ADDITIVE | Added provisions or removed requirements without breaking/unknown observations |
| BREAKING_STRUCTURAL_CHANGE | Removed/retargeted provisions or added obligations |
| COMPATIBILITY_UNKNOWN | Insufficient canonical evidence or unmeasured behavior/content change |
| INCOMPATIBLE_SCHEMA | Unsupported manifest interpretation; fail closed |
| PACKAGE_IDENTITY_FAMILY_CHANGED | Namespace/name changed; not an ordinary version upgrade |

Dimensions cover family, schema, exports, dependencies, required capabilities, provided capabilities, tier, entrypoints, content and ordered documents. Version and provenance are context, not classification inputs. A known structural result remains explicitly bounded to the supplied evidence.

## Export, entrypoint and schema rules

P14.4 uses existing `SymbolReference.identity` as the package-facing export key. P14.10 compares the full canonical symbol reference: AIR fingerprint, kind, identity and module. Existing keys plus exact references are unchanged; added keys are additive; removed keys or the same key with a different reference are breaking. No canonical identity equivalence is inferred. A changed AIR fingerprint therefore conservatively counts as retargeting, even when display spelling is unchanged.

Exports present in either manifest require supplied P14.4 indexes to admit canonical declaration evidence. Missing evidence records CANONICAL_EXPORT_EVIDENCE_MISSING and yields unknown unless a stronger breaking/family/schema finding exists. Supplied indexes with the wrong exact provider content fail EXPORT_EVIDENCE_CONTENT_MISMATCH. Export-name collisions fail instead of shadowing. Private declarations are not inferred as exports.

Entrypoints are P14.1 validated directive references. Add/remove/retarget rules are identical to export structural rules. An entrypoint declaration or compatibility result gives no execution permission.

Only current `apexforge.package/v1` is interpreted. Raw unknown schema is normally rejected by P14.1 admission; a controlled adversarial fixture verifies P14.10 still returns INCOMPATIBLE_SCHEMA if unsupported schema evidence reaches comparison. No schema migration or reinterpretation occurs.

## Capability, dependency and tier evolution

Capability identities match exactly under existing P14.5 rules. Adding a required capability is breaking; removing one is additive from the requirement perspective. Adding a provided capability is additive; removing one is breaking. Replacing an identity records removal and addition, without implication, fuzzy matching or versions.

All P14.1 dependency declarations are required exact coordinates. Adding one is breaking; removing one is additive from availability-obligation perspective. A same-family exact dependency coordinate/version change is COMPATIBILITY_UNKNOWN because no compatibility evidence for those dependency versions is supplied. No recursive dependency comparison, registry query or solving occurs.

Package classification uses actual P14.1 PackageTier. Any tier transition, including absent/present, is breaking. No unsupported package-kind categories or conversion semantics were introduced.

## Metadata, content and behavioral limits

Non-identity metadata remains excluded according to P14.1. Metadata-only changes produce identical structural contracts and do not change report identity.

A content fingerprint difference alone is not breaking: version or provenance changes can alter package content identity while measured public structure remains identical. Changed content descriptors produce CONTENT_BEHAVIOR_NOT_ESTABLISHED/unknown, not a guessed semantic verdict. Ordered document changes likewise remain unknown. Provenance is preserved separately and does not prove compatibility or trust.

Unchanged canonical symbol identity states an exact structural fact. It does not prove function signatures, runtime effects or behavioral equivalence. No version-number/semantic-version policy is claimed.

## Determinism and immutable evidence

Changes are ordered by canonical JSON of their full records. Dimension order is fixed. JSON uses sorted keys, compact separators, ASCII escaping, UTF-8 and no locale/host paths/timestamps/object repr. Equivalent independently constructed manifests and input permutations yield identical reports.

Compatibility fingerprint: SHA-256 of `apexforge.package-compatibility/v1` + NUL + canonical record UTF-8. It commits to exact old/new content identities, provenance context, dimensional evidence, ordered changes and classification. It is not a package identity, trust verdict or authorization.

Outputs are frozen dataclasses and contain tuples, frozen validated package records or canonical JSON strings. Serialization returns detached mutable dictionaries without exposing mutable internal state. These are generated analysis results, not raw JSON parsers or proof of authenticated producer claims.

## Migration planning and impact

`plan_migration(old, new, graph=None, lock=None, old_exports=None, new_exports=None)` takes the caller-selected exact target; it never selects latest or discovers candidates. It generates an immutable MigrationPlan with the report, exact direct/transitive consumer identities, ordered MigrationStep records, supplied graph/lock fingerprints and lock-refresh indication.

Each step includes a known consumer identity or null for a package/global obligation, a subject reference, fixed reason, obligation kind and MANUAL_OR_EXTERNAL_ACTION_REQUIRED. The enclosing report preserves exact old/new provider identities. Obligations include updating an exact direct dependency, solving/validating a new graph externally, reviewing removed/retargeted exports and entrypoints, reviewing capability/dependency/content changes, separately checking target trust, refreshing a lock externally, and requiring a distinct publication coordinate for same-coordinate changed content.

No source/import/.apexdoc rewriting, manifest mutation, package rename transformation, lock regeneration or executable migration occurs. A family change receives a review obligation, not a mechanical rename. Plans can describe an additive upgrade as well as breaking/unknown evolution; planning does not promote unknown to compatibility PASS.

### Direct and transitive impact

The optional graph must be an existing successful P14.2 graph containing the exact old coordinate and content. Wrong binding fails MIGRATION_OLD_GRAPH_BINDING_MISMATCH. A reverse dependency adjacency is built from its explicit edges; iterative traversal finds direct requiring packages and downstream transitive exposure. Direct consumers follow P14.4/P14.5 DIRECT_ONLY visibility. Transitive consumers are reported as exposed, not asserted broken or given direct-use evidence they do not possess.

Canonical consumer ordering uses the canonical exact-node reference. The graph fingerprint records the supplied dependency evidence. No consumer/project/filesystem/registry discovery occurs. Complexity is O(V+E) traversal plus deterministic output sorting and serialization. The focused large fixture has 1,101 nodes: one direct affected package and 1,099 transitive exposures, without recursion failure.

### Lock impact and immutable publication boundary

A supplied lock is inspected for exact old content. Same-coordinate wrong content fails MIGRATION_OLD_LOCK_BINDING_MISMATCH. If both graph and lock are supplied, their resolutions must match exactly. LOCK_REFRESH_REQUIRED is true only when the exact old content is locked and the target content differs. Missing unrelated locked packages do not trigger refresh. No lock is modified.

Changed content at an unchanged coordinate receives REQUIRE_DISTINCT_PUBLICATION_COORDINATE. This preserves P14.9 immutable publication policy; it neither overwrites published records nor claims the target is admissible. New content normally needs a caller-chosen new exact version, not automatic version allocation.
